# How this repository was verified

The project was built and run in a sandbox **without access to nuget.org** (the egress proxy rejects
`api.nuget.org`). `dotnet restore` of `Google.OrTools` and xUnit was therefore impossible there. Instead of
claiming results that were never produced, the code was compiled and executed against locally built
stand-ins with the same APIs. **None of the stand-ins are part of this repository.**

| Delivered reference | Used in the sandbox | Fidelity |
| --- | --- | --- |
| `Google.OrTools` 9.15.6755 (NuGet) | An assembly named `Google.OrTools` compiled from the **official OR-Tools C# sources** (`ortools/sat/csharp/*.cs`, `ortools/util/csharp/*.cs`), C# classes generated by `protoc` from the official `cp_model.proto` / `sat_parameters.proto`, and the **official native CP-SAT engine** `libortools.so.9` from the `ortools==9.15.6755` PyPI wheel. The SWIG glue is replaced by P/Invoke to the public C API `SolveCpModelWithParameters`. | Model building (`CpModel`, `LinearExpr`, `AddHint`, …) is the real C# code; solving is the real native engine. Only `Solve` + string parameters are bridged (no callbacks), and the project uses no callbacks. |
| `xunit` 2.9.2 + `xunit.runner.visualstudio` + `Microsoft.NET.Test.Sdk` | A small xUnit-compatible API (`Fact`, `Theory`, `InlineData`, `IClassFixture`, `Assert.*` with xUnit semantics) and a reflection runner. | Tests compile unchanged against real xUnit. xUnit analyzers did not run in the sandbox. |
| `Npgsql.EntityFrameworkCore.PostgreSQL` 8.0.11 (+ EF Core 8.0.11, Npgsql 8.0.6) | Compiled from the **official tagged sources** (`dotnet/efcore` v8.0.11, `npgsql/npgsql` v8.0.6 incl. its source generator, `npgsql/efcore.pg` v8.0.11) | Same code as the packages; only the build scripts differ (analyzers off, no package signing for EF). |
| PostgreSQL server | PostgreSQL **16.15** (Ubuntu), local throw-away cluster | real server |
| ASP.NET Core 8 | the real shared framework (installed with the SDK) | identical |

The harness copies the repository to a scratch folder and swaps only the three package references
(`PackageReference` → local `ProjectReference`). The source files are compiled exactly as delivered, with
`TreatWarningsAsErrors=true`.

## What to do on a machine with NuGet access

```bash
dotnet restore          # if 9.15.6755 is not available, use the latest Google.OrTools 9.x — the API used is stable
dotnet build -c Release
dotnet test -c Release
```

If the xUnit analyzers (shipped with the real `xunit` package) report a style warning, `TreatWarningsAsErrors`
turns it into a build error. Fix the reported assertion style or relax that rule in `Directory.Build.props`.
